# Forge — Architecture (v0 Prototype)

## 1. High-Level Shape

```
                         ┌─────────────────────────┐
                         │        forge CLI          │   src/cli.ts (commander)
                         │  (commands/*.ts)          │
                         └────────────┬─────────────┘
                                       │ reads/writes
                                       ▼
                         ┌─────────────────────────┐
                         │     .forge/ state store   │   core/store.ts
                         │  forge.yaml, runs, logs   │
                         └────────────┬─────────────┘
                                       │
              ┌────────────────────────┼────────────────────────┐
              ▼                        ▼                        ▼
   ┌────────────────────┐   ┌──────────────────────┐  ┌──────────────────────┐
   │   core/simDb.ts      │   │  core/mockApi.ts       │  │  core/policyEngine.ts  │
   │ synthetic data gen   │   │ fake 3rd-party APIs    │  │ intercept/block/rewrite│
   └────────────────────┘   └──────────────────────┘  └──────────────────────┘
              ▲                        ▲                        ▲
              └────────────────────────┴────────────────────────┘
                                       │
                         ┌─────────────────────────┐
                         │   core/fakeAgent.ts        │
                         │ scripted "AI agent" that   │
                         │ emits realistic operations │
                         └─────────────────────────┘
```

In v0, there is no real daemon process and no real OS-level syscall
interception — that's intentionally deferred (see `04-ROADMAP.md`). Instead:

- `core/fakeAgent.ts` is a **scripted operation generator**: given a "task"
  string, it yields a deterministic (but randomized-feeling) sequence of
  fake operations (`db.query(...)`, `fs.write(...)`, `http.connect(...)`)
  that *resembles* what a real coding agent attached via syscall interception
  would actually do.
- `core/policyEngine.ts` evaluates each operation the fake agent emits and
  decides: `pass`, `rewrite` (with a corrected operation + reason), or
  `block` (with a reason, after which the fake agent "self-corrects" in the
  script, mirroring how a real agent would receive the block reason as
  context and retry).
- `core/simDb.ts` and `core/mockApi.ts` provide just enough fake state
  (record counts, schema field lists) for the policy engine and run report to
  reference real-feeling numbers (e.g. "50,241 synthetic rows", "11,843 / 12,000
  sessions passed").

This keeps the prototype honest: it does not pretend to do real syscall
interception, but it produces the *exact same artifacts* (live log, run report,
diff, approval gate) that the real product would, so the CLI/UX and data
shapes can be validated and iterated on before the harder systems-level work
begins.

```
forge-prototype/
├── docs/                        # this spec package
├── src/
│   ├── cli.ts                   # commander setup, registers commands
│   ├── types.ts                 # shared TypeScript types
│   ├── commands/
│   │   ├── init.ts              # forge init
│   │   ├── db.ts                # forge db link / forge db status
│   │   ├── mock.ts               # forge mock add / forge mock list
│   │   ├── sim.ts                # forge sim add / forge sim list
│   │   ├── attach.ts             # forge attach <agent>
│   │   ├── run.ts                # forge run
│   │   ├── log.ts                # forge log --follow
│   │   ├── diff.ts               # forge diff <run-id>
│   │   ├── approve.ts            # forge approve <run-id>
│   │   └── connect.ts            # forge connect/disconnect <provider>
│   └── core/
│       ├── store.ts              # reads/writes forge.yaml + .forge/ state
│       ├── simDb.ts              # synthetic data generator
│       ├── mockApi.ts            # mock 3rd-party API registry
│       ├── policyEngine.ts       # intercept/block/rewrite logic
│       ├── fakeAgent.ts          # scripted operation generator
│       ├── runner.ts             # orchestrates a `forge run` end to end
│       └── ui.ts                 # terminal output helpers (color, log lines, boxes)
├── forge.yaml                    # generated by `forge init` (gitignored example may exist)
├── .forge/
│   ├── schema.json               # captured "DB schema" from `forge db link`
│   ├── sims/                     # sim YAML files
│   ├── runs/                     # one JSON file per run: full state + events
│   ├── reports/                  # human-readable run reports (rendered + saved)
│   └── diffs/                    # unified diff patches per run
├── package.json
└── tsconfig.json
```

## 3. Command Responsibilities

### `forge init`
- Prompts (or accepts flags) for: project name, stack (can be a free-text
  guess/label, no real detection needed in v0), policy preset
  (`default`/`strict`).
- Writes `forge.yaml` (see `03-FORGE-YAML-SPEC.md`).
- Creates `.forge/` subdirectories.
- Idempotent: refuses to overwrite an existing `forge.yaml` unless `--force`.

### `forge db link <connection-string> [--sim-only] [--rows <n>]`
- Does **not** actually connect to a real database in v0. Parses the
  connection string only to extract a display name/type
  (e.g. detects `postgres://` vs `mysql://` vs `mongodb://` from the prefix).
- Generates a **fake schema** (a fixed, reasonable e-commerce-shaped schema:
  `users`, `orders`, `order_items`, `coupons`, `sessions` — see
  `core/simDb.ts`) — this stands in for "schema introspection."
- Calls `simDb` to generate N synthetic rows per table (default 50,000 total,
  distributed across tables) and stores summary counts.
- Writes `.forge/schema.json` and updates `forge.yaml`'s `data.databases`.
- Prints a real-feeling progress sequence (see `05-CLI-UX-SPEC.md` for exact
  expected output).

### `forge mock add <service> [--preset <name>]`
- Registers a mock API in `forge.yaml` (`data.mocks`).
- Ships with at least two presets in v0: `stripe` (ecommerce: charges,
  refunds, declined-card scenario) and `sendgrid` (email capture).
- `core/mockApi.ts` just needs to hold static preset definitions (scenario
  names, fake "endpoint" labels) — no real HTTP server needs to run in v0,
  though leaving a clean seam to add a real `http.createServer` mock later is
  good practice.

### `forge sim add [--file <path>] [--user-type <type> --count <n>]`
- Two input modes per the PRD: a YAML file path (declarative/scripted sim
  definition, see `04-SIM-YAML-SPEC.md`) OR inline flags for a quick
  persona/edge-case addition.
- Validates the YAML against the sim spec shape (best-effort — v0 can do
  light validation, not full JSON-schema enforcement, but should at least
  check required top-level keys exist).
- Stores the sim reference in `forge.yaml`'s `simulations` list and copies/
  writes the YAML into `.forge/sims/`.

### `forge attach <agent> --scope <glob> [--read-only <glob>...]`
- Records an "attached agent" session in `.forge/state.json` (or similar):
  agent name, scope glob(s), read-only globs, timestamp.
- In v0 there's only ever one attached agent at a time (multi-agent
  negotiation is explicitly out of scope — see roadmap) but the data shape
  should already accommodate a `sessionId` so it's easy to extend later.
- Does not start the run — just registers intent. `forge run` consumes this.

### `forge run [--task "<description>"] [--policy <preset>] [--exit-on-block]`
This is the centerpiece command. It should, in order:

1. Load `forge.yaml` + attached agent state. If nothing is attached, error
   with a helpful message telling the user to run `forge attach` first.
2. Generate a `runId` (e.g. `run-<n>` incrementing, or short uuid).
3. Print a "run started" header (project, agent, scope, task).
4. Call `core/fakeAgent.ts` to get an ordered list of operations for the given
   task (or a default task if none provided — see fakeAgent spec for the
   built-in scripted scenario, which should match the checkout-flow narrative
   used throughout the docs so it's consistent).
5. For each operation, call `core/policyEngine.ts` to evaluate it against the
   active policy rules. Stream a log line per operation as it's evaluated
   (`pass` / `rewrite` / `block`), with realistic timing (small artificial
   delays, e.g. 150–500ms between lines, so it reads like a live process, not
   an instant dump).
6. After all "code" operations are evaluated, run the registered simulations:
   print session counts ramping up (e.g. partial counts updating) and a final
   pass/fail count per sim, with at least one sim intentionally showing a
   partial failure (to demonstrate the "edge case caught" narrative).
7. Assemble a run report: file change summary (fake but consistent diff
   content — see fakeAgent spec), policy stats (intercepts, blocks), sim
   results, overall pass rate.
8. Write `.forge/runs/<runId>.json` (full structured state),
   `.forge/diffs/<runId>.patch` (unified-diff-style text), and
   `.forge/reports/<runId>.json` (the report summary).
9. Print a closing summary block with next-step hints
   (`forge diff <runId>`, `forge approve <runId>`).
10. Respect `--exit-on-block`: if any operation was hard-blocked and not
    successfully auto-corrected, exit with a non-zero process exit code
    (useful for CI framing later, even though CI isn't wired up in v0).

### `forge log --follow [--run <run-id>]`
- If a run is currently the "latest", re-streams its stored events with the
  same artificial pacing as a live tail (since v0 has no real background
  process to attach to). `--run <id>` targets a specific past run.
- Without `--follow`, just dumps the event list immediately.

### `forge diff <run-id>`
- Renders the stored `.forge/diffs/<run-id>.patch` with basic colorization
  (green `+` lines, red `-` lines) — see `core/ui.ts`.

### `forge approve <run-id>`
- Reads the run report. If `forge.yaml`'s `approve.require_pass_rate` is set
  and the run's sim pass rate is below it, refuse to approve unless
  `--force` is passed, and explain why.
- On success: marks the run as `approved: true` with a timestamp and
  approver note in the stored run JSON, prints a confirmation, and — only if
  `forge.yaml` shows a connected CI/CD integration — prints a clearly labeled
  **simulated** "would now trigger CI" message (no real network call in v0).

### `forge connect <provider>` / `forge disconnect <provider>`
- v0 can fully stub the actual integration (no real GitHub API calls).
  It should still: update `forge.yaml`'s `mode` and `integrations` block,
  print a realistic confirmation sequence, and be cleanly reversible via
  `forge disconnect`.

## 4. Core Module Contracts

### `core/store.ts`
Responsible for all reads/writes of `forge.yaml` and everything under
`.forge/`. Should expose a small, clear API, roughly:

```ts
loadForgeYaml(): ForgeConfig | null
saveForgeYaml(config: ForgeConfig): void
ensureForgeDirs(): void
saveRun(run: RunRecord): void
loadRun(runId: string): RunRecord | null
listRuns(): RunRecord[]
nextRunId(): string
```

### `core/policyEngine.ts`
Pure-ish function(s) that take an operation and the active policy rules and
return a verdict. Should not do any I/O itself (keep it testable):

```ts
evaluateOperation(op: AgentOperation, policy: PolicyConfig): PolicyVerdict
```

Where `PolicyVerdict` includes the original op, the verdict
(`pass`/`rewrite`/`block`), an optional rewritten operation, and a
human-readable `reason`. See `06-POLICY-ENGINE-SPEC.md` for the exact rule
set to implement in v0.

### `core/simDb.ts`
```ts
generateSchema(connectionString: string): DbSchema
generateSyntheticRows(schema: DbSchema, totalRows: number): RowCounts
```

### `core/mockApi.ts`
```ts
getPreset(service: string): MockApiPreset | null
listPresets(): MockApiPreset[]
```

### `core/fakeAgent.ts`
```ts
generateOperations(task: string, scope: string): AgentOperation[]
generateFileDiff(operations: AgentOperation[]): FileDiff[]
```
This is the module most worth keeping flexible/extensible — see
`07-FAKE-AGENT-SPEC.md` for the exact built-in scenario script to implement,
written so the rest of the system (policy engine, sim runner, report) has
realistic, consistent content to react to.

### `core/runner.ts`
Orchestrates steps 4–9 of `forge run` above, calling into `fakeAgent`,
`policyEngine`, and the sim runner logic, and using `core/ui.ts` for all
terminal output (so output styling is centralized, not scattered across
commands).

### `core/ui.ts`
Centralized terminal output helpers: colored log line prefixes (`✓`/`⚠`/`✗`),
boxed summary panels (can use `boxen`), spinners (`ora`) for the brief
"generating synthetic rows..." moments, and a small `sleep(ms)` helper used to
pace streamed output realistically.

## 5. Data Flow for `forge run` (Sequence)

```
forge run
   │
   ▼
runner.ts: load config + attached agent
   │
   ▼
fakeAgent.generateOperations(task, scope)  ──▶  [op1, op2, op3, ...]
   │
   ▼
for each op:
   policyEngine.evaluateOperation(op, policy) ──▶ verdict
   ui.printLogLine(verdict)         (paced with sleep)
   if verdict.rewrite: op = verdict.rewrittenOp   (fakeAgent "self-corrects")
   │
   ▼
simRunner: for each registered simulation:
   compute session pass/fail counts (weighted random, but seeded so
   one sim always shows the "edge case" partial failure)
   ui.printSimProgress(...)
   │
   ▼
assemble RunReport { diff, policyStats, simResults, passRate }
   │
   ▼
store.saveRun(...)  +  write diff + report files
   │
   ▼
ui.printRunSummary(report)
```

## 6. Why This Architecture (Design Rationale)

- **Pure functions for policy + fake agent logic** mean the most "interesting"
  parts of the system (the rules, the scenario script) are trivially testable
  and swappable later when real syscall interception and real LLM agents
  replace the fakes — the CLI commands and runner orchestration barely need
  to change.
- **Everything persisted as JSON/YAML under `.forge/`** means a human (or
  Claude Code in a later session) can inspect exactly what happened without
  re-running anything, and it gives a natural seam for an eventual `forge tui`
  or web dashboard to read the same files.
- **No real daemon process in v0** deliberately avoids the complexity of
  process management, IPC, and background services before the CLI UX and data
  shapes are validated. The `core/store.ts` + JSON files *are* the "daemon
  state" for now; a real daemon can be introduced later as a thin process
  that wraps the same core modules.
